Engineering write-ups

Retries and idempotency

A consumer can commit a write and crash before acknowledging the message. When the broker redelivers it, record the event ID in the same database transaction as the business write. A unique constraint lets only one attempt apply the change.

For external effects, pass the same idempotency key downstream on each retry. Limit retries to transient failures, apply exponential backoff with jitter, and send exhausted events to a dead-letter queue for review.

Diagnosing Kafka consumer lag

Start with lag by partition and the age of the oldest unprocessed event. Compare the producer rate with the consumer processing rate. Broad lag can indicate a downstream bottleneck, while one lagging partition often points to a hot key.

Check database time, rebalance frequency, and partition assignment before scaling. A group can only use as many parallel consumers as it has partitions. Adding consumers beyond that limit leaves them idle.

PostgreSQL indexing mistakes

Start with the slow query and its execution plan. In a safe environment with representative data, compare estimated and actual row counts and inspect buffer reads using EXPLAIN (ANALYZE, BUFFERS).

Design indexes around the query's filters and ordering, then rerun the same workload after the change. Check write latency and index size as well as read latency. An index can improve one query while adding cost to every insert.
